# R2: every ecological number becomes a registered knob

R1 put every existing config-struct field in a registry table (`cubarium_voxel::registry`,
one table per crate). It has a coverage test, ranges, `--set`, `params.toml`, and the
generated `design/parameters.md`. R2 moves the numbers that are still `const`s or inline
literals into those structs, and gives each one a registry row.

Wrysk, 2026-10-01: a large tuning pass over all parameters comes later, so every magic
number has to be a tunable knob (WORKING_POLICY "Every number is a knob"). R2 therefore
covers **every ecological number**, not only the ones `parameters.tsv` marks evolvable.

## Three packages, one per worktree, in parallel

- **R2-fauna**: `crates/cubarium-voxel-fauna` and the fauna side of `cubarium-voxel-sim`.
- **R2-flora**: `crates/cubarium-voxel-flora` and the flora side of `cubarium-voxel-sim`.
- **R2-world**: the water, weather, soil and generator numbers in `crates/cubarium-voxel`,
  plus `world.landform`. R1 left landform opaque: TOML and `--set` replace it whole, and
  its own recipe validators check it. Give its numbers rows, including the tsv's
  evolvable `inventory_m`, `aquifer_head_m`, `water_level_m`, `soil_m` and `grove_soil_m`.

Where to start: the audit's `design/7_Research/ecology-parameter-audit-2026-09-28/parameters.tsv`.
Rows whose `exposure` is a `const` or an inline literal are your list. Then sweep your crate
for numeric literals in sim logic the audit missed, including P1's predation and parasite
code. The training/search harness numbers (tsv subsystem `harness`) are R3's, not yours.

## What counts as ecological

- **Is a knob:** any number that sets how the world, a plant or an animal behaves. That
  includes rates, thresholds, sizes, durations, fractions, costs, probabilities, clock
  factors, and "magic" shaping constants such as curve exponents and smoothing time
  constants.
- **Stays a `const`:** pure numerics. That means tolerances, epsilons, iteration caps,
  cache and buffer sizes, unit conversions (`3600.0`), and mathematical constants.
- **When unsure, make it a knob,** and say so in your return.

## Rules

- **No number changes.** Every default equals today's value. R1's "defaults unchanged" and
  coverage tests must stay green.
- **Each moved number:**
  - becomes a field in the config struct that owns similar numbers;
  - gets a doc comment with its unit and meaning;
  - gets a registry row with unit, a hard validity `range` and a `search` interval. Use the
    tsv values where it has them; otherwise use plausible bounds with provenance
    "placeholder".
- **Thread the config to the call site.** Don't re-read a global. If a helper used a
  `const`, it takes the value as a parameter or reads it from the config it already gets.
- **Snapshot schema:** if a moved field lands in a struct the snapshot stores, bump to the
  next free schema. Always fresh, no migration. Only R2-fauna and R2-flora may need this.
  To avoid colliding on numbers, R2-fauna takes the next free fauna schema and R2-flora
  the next free flora schema.
- **Don't regenerate `design/parameters.md`;** the integrator does it after merging all
  three. Don't touch another package's crate. If you need a change there, list it.
- **Git:** work in your own worktree, with `CARGO_TARGET_DIR` inside it. Commit in logical
  steps with explicit paths only. Never `commit -a`, never merge to main.
- **CPU:** prefix builds with `taskset -c 8-15,24-31` and set `CARGO_BUILD_JOBS=8` (three
  packages run at once). No sims, benches or long runs.
- **Check:** run `cargo nextest run -p <crate>` for each crate touched, and
  `cargo build --examples -p <crate>` where examples change.
- **Return (≤40 lines):**
  - commits as SHA plus one line;
  - the number of constants and literals moved, and rows added;
  - anything you left as a `const` that a reader might call ecological, and why;
  - any cross-crate change you need.

  Stop your background shells first.
